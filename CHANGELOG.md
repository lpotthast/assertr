## [Unreleased]

## [0.7.0] - 2026-08-30

### Added

- `BTreeSet`, `BTreeMap`, and `LinkedList` are supported subjects now. The set and map families no longer live in the
  `std` module, so `no_std` builds get set and map assertions for the first time: `BTreeSet` and `BTreeMap` are `alloc`
  types, and only the `HashSet` / `HashMap` implementations are gated on the `std` feature.
- `contains_all(expected)` on every collection, plus the streaming `into_iter_contains_all(expected)` counterpart.
  `contains_all` used to exist for `HashSet` only, but nothing about it is set-specific, so slices, arrays, `Vec`,
  `VecDeque`, `LinkedList`, and every custom `Collection` gained it. The streaming form iterates once and stops as soon
  as every expected element has been found.
- Sets gained `contains_matching`, `contains_satisfying`, `does_not_contain_matching`, `does_not_contain_satisfying`,
  and the whole `contains_exactly_in_any_order{,_matching,_satisfying}` family.
- Maps gained `contains_entry_satisfying`, `contains_exactly_entries_matching`, and
  `contains_exactly_entries_satisfying`. The exact variants pair each expected key with a predicate or assertion closure
  for its value, reject missing and unexpected keys, and enforce one-to-one entry cardinality: repeated expected keys
  cannot reuse one actual map entry.
- The structured failure type `AssertionFailure`, exported from the crate root and the prelude. It exposes the source
  location, subject name, description, per-failure details, and chain-level user messages of a captured failure as
  public fields, so failures can be inspected without parsing text. Its `Display` implementation produces the
  human-readable form, which is rendered only at the panic or display boundary.
- The `assert_that_owned!` macro, the ownership-taking counterpart to the now-borrowing `assert_that!` (see *Changed*).
  It is only needed for assertions that consume their subject, such as `panics()` on a closure or the terminal iterator
  assertions. In particular, a 0.6 call such as `assert_that!(v.into_iter()).contains(2)` still compiles after the
  upgrade, but fails at runtime because the iterator is borrowed. Change it to
  `assert_that_owned!(v.into_iter()).contains(2)`.
- Conditions can be passed by reference: `AssertrCondition` (the renamed `Condition` trait, see *Changed*) is
  implemented for every `&C` where `C` is a condition, so one condition instance can be used in several assertions.
- The fluent alias `be(condition)` for `is(condition)`. Its synonym `has(condition)` gets no alias, because `have`
  already denotes the per-element condition assertion on iterables.
- Fluent aliases for the assertion traits that were still missing them: `IntoIteratorAssertions` (the `into_iter_`
  prefix stays: `into_iter_contain`, `into_iter_not_contain`, `into_iter_have_length`, ...), `AsyncFnOnceAssertions`
  (`panic_async`, `not_panic_async`), `ProgramAssertions` (`exist`, `exist_and`), `CommandAssertions` (`have_arg`), and
  `ReqwestResponseAssertions` (`have_status_code`, `be_success`, ...). The alias generator learned the verbs `panics` ->
  `panic` and `needs_*` -> `need_*` for this. Generated aliases inherit the original method's documentation and
  attributes, including `#[must_use]` and `#[deprecated]`. Every alias starts its documentation with a separate
  introductory paragraph linking back to the original. Parameter patterns are normalized so every argument is
  forwarded.
- `AssertThat::track_assertion` and `AssertThat::fail_with_details` are public now, supporting hand-written
  assertions. Without the tracking hook, a passing custom assertion did not count towards its chain, so a
  `capture` / `verify` closure containing only custom assertions panicked as if it had been empty. Without
  `fail_with_details`, per-failure evidence had to go through `add_detail_message`, which also applies to every later
  failure of the chain. Both are documented and covered by `assertr/tests/custom_assertions.rs`.
- Public API documentation now covers every exported source item and the matcher structs and fields generated by
  `AssertrEq`. Both crates deny `missing_docs`, and a derive compile fixture applies the lint to generated items. The
  crate root includes a custom-assertion guide, and the API docs consistently describe subjects, expected values,
  ownership, capture mode, renderer capabilities, extraction, iterator termination, borrowed map lookup, and
  integration error behavior. A second accuracy pass clarified conservative `needs_drop` results, panic boundaries,
  path metadata errors, repeated HTTP headers, embedded versus hosted `no_std`, and `RefCell` borrow state while
  removing repeated generic inventories and `must_use` examples.
- `LICENSE-MIT` and `LICENSE-APACHE` files, included in both published packages. The crates were already declared as
  `MIT OR Apache-2.0`.
- The floating-point classifications `is_normal()` and `is_subnormal()`, gated on `std` or `libm` like `is_nan()`,
  `is_finite()`, and `is_infinite()`.
- `TokioMutexAssertions::has_value_satisfying`, which tries to lock a Tokio mutex and runs a capture-mode assertion
  closure against its data. The callback accepts `FnOnce`, like the other single-value `_satisfying` assertions. A
  locked mutex fails immediately. Failures from the contained assertions are reported as details of one mutex-level
  failure.
- More `reqwest` response assertions. Next to `has_status_code` there are the status classes `is_informational`,
  `is_success`, `is_redirection`, `is_client_error`, and `is_server_error`, the header assertions `has_header`,
  `does_not_have_header`, and `has_header_value`, and the projections `get_header(name)` into a `HeaderValue`, the
  `async` `get_text()` into the body, and, with `serde-json` enabled, the `async` `get_json::<T>()` into the
  deserialized body. Reading a body consumes the response, so `get_text()` and `get_json()` take it by value and require
  `assert_that_owned!` (or `.must_owned()`) and reject a borrowed response synchronously, before returning their future.
  `get_text()` requires no renderer capability; `get_json()` requires only `ValueRenderer<String>` and renders an
  invalid body through the active renderer next to the `serde_json` error and target type. Each projection counts as
  one assertion, reports failures at the projection call site, and keeps operation-specific evidence on that failure
  instead of leaking it into later failures. Every response failure attaches the request URL as a detail, and
  `has_status_code` says what it compared instead of a bare `Expected: 200 OK / Actual: 404 Not Found`.
- The `serde-json` and `serde-toml` features, which split the former all-or-nothing `serde` feature into the two
  conversions it contains. `serde` remains as the group enabling both, so existing feature lists keep working, but a
  project that only needs `json()` / `as_json()` no longer compiles a TOML parser. `serde-json` pulls 7 crates and
  `serde-toml` 9, where `serde` pulls 13. The TOML serializer was updated to `toml` 1.1.

### Changed

- **Breaking:** The per-type `ArrayAssertions`, `SliceAssertions`, `VecAssertions`, `VecDequeAssertions`,
  `HashSetAssertions`, and `HashMapAssertions` were replaced by the generic `CollectionAssertions`,
  `SequenceAssertions`, `SetAssertions`, and `MapAssertions`. Each is blanket-implemented for every subject implementing
  its new extension trait, so all containers of a family share one implementation, one set of bounds, and one set of
  diagnostics. `Collection` is implemented for `[T]`, `[T; N]`, `Vec<T>`, `VecDeque<T>`, `LinkedList<T>`, `BTreeSet<T>`,
  and `HashSet<T, S>`, and `Collection` / `Sequence` forward through every shared reference to an implementation. `Set`
  for `BTreeSet` and `HashSet`, and `Map` / `MapLookup` for `BTreeMap` and `HashMap`, forward through shared references
  in the same way.
  Implementing the extension trait gives a custom type the same assertions. The extension traits are not exported from
  the prelude. Implementors import `Collection`, `Sequence`, `Set`, or `Map` from the corresponding assertion module.
  The new `Collection` and `Map` extension traits expose only their elements or entries; `assertr` renders the
  surrounding container structure itself. `Collection::STYLE` and the public `CollectionStyle::{List, Set}` metadata
  select that structure independently of the optional `TYPE_NAME` prefix. The default is `List`. Custom set-like
  implementations must select `Set`. `AssertThat::render_values` and `EqContext::render_values` require the style as an
  argument, so custom diagnostic code cannot accidentally fall back to list syntax. This keeps named list-like and
  unnamed set-like collections from being rendered with the wrong delimiters.
  `CollectionAssertions` holds the order-free assertions. The `Sequence: Collection` marker guards the three
  order-sensitive ones (`contains_exactly`, `contains_exactly_matching`, `contains_exactly_satisfying`) in
  `SequenceAssertions`. Sets are collections but not sequences, so calling those on a set is a compile error (its
  diagnostic recommends `contains_exactly_in_any_order`) instead of a test that only passes because the elements
  happened to be written in iteration order. For sequence subjects, method names and behavior are unchanged. The set
  relations (`is_subset_of`, `is_superset_of`, `is_disjoint_from`) print the expected set with its type name now
  (`Expected superset: BTreeSet {..}`) and add a detail when the two sets are of different types. The lookup bounds for
  map-key methods are described separately below. Migration:

  | before                                                                 | after                                                         |
  |------------------------------------------------------------------------|---------------------------------------------------------------|
  | `use assertr::prelude::*;` plus a method call                          | unchanged                                                     |
  | explicit `use ...::core::slice::SliceAssertions;` (and friends)        | `use assertr::assertions::collection::CollectionAssertions;`  |
  | `...::core::array` / `core::slice` / `alloc::vec` / `alloc::vec_deque` | `assertr::assertions::collection`                             |
  | explicit `use ...::std::hashset::HashSetAssertions;`                   | `use assertr::assertions::set::SetAssertions;`                |
  | explicit `use ...::std::hashmap::HashMapAssertions;`                   | `use assertr::assertions::map::MapAssertions;`                |
  | `contains_exactly::<E, EE>(..)` turbofish on a slice subject           | `contains_exactly::<E>(..)` (the collection type is inferred) |
  | `.contains_exactly(..)` on a set                                       | `.contains_exactly_in_any_order(..)`                          |
  | `.is_subset_of(boxed_set)`                                             | `.is_subset_of(*boxed_set)`                                   |

  The set relations (`is_subset_of`, `is_superset_of`, `is_disjoint_from`) take the other set by value as any `Set` with
  the same item type instead of `impl Borrow<HashSet<T, S2>>`. A `HashSet` can be compared against a `BTreeSet` this way
  (a failure then names both set types), and type inference stays unambiguous now that `&S` is itself a `Set`. The only
  argument form this drops is a `Box<HashSet<..>>`. Dereference it.
- **Breaking:** `contains_exactly_in_any_order` on collections, owned iterators, and borrowed `IntoIterator` subjects
  compares through `AssertrPartialEq<E, R>` now, like the sibling equality assertions, so it accepts a different
  expected element type and custom `AssertrPartialEq` implementations. Ordinary inferred calls are unchanged. A call
  that explicitly supplied the old `AsRef` wrapper type as generic argument must drop that turbofish or supply the
  expected element type instead.
- **Breaking:** Every map assertion that queries keys dispatches through the new extension trait `MapLookup<Q>`, which
  carries the map's own lookup bounds: a `HashMap` needs `K: Borrow<Q>` and `Q: Hash + Eq`, a `BTreeMap` needs
  `K: Borrow<Q>` and `Q: Ord`, exactly what the maps themselves require. Lookups therefore use the native
  `get_key_value` instead of linearly scanning entries, and a `HashMap<String, _>` or `BTreeMap<String, _>` is
  queryable with a `str`. Bulk expected keys resolve their native lookup type through the new `MapKeyQuery<K>`
  extension trait, so `contains_keys(["a"])` and the whole `contains_exactly_entries` family accept `str` views of
  `String` keys without exposing an inference-ambiguous `Q` generic at every call site. The ordinary `Borrow<K>` input
  forms are provided, and a custom expected-key wrapper or borrowed view implements `MapKeyQuery<K>` to name the
  `MapLookup` query it supplies. The exact assertions identify unexpected entries through the same lookup, so neither
  they nor `contains_keys` impose `Hash` or `Ord` on the key type beyond what its map already demands. `Map::Key` has
  no universal `Eq` bound: lookup semantics belong to `MapLookup`, and exact assertions identify stored entries by
  identity.
  String literals are passed as written. Owned key expressions need an explicit borrow, an explicit value-type turbofish
  on `contains_entry` / `does_not_contain_entry` needs a second `_` for the query type, and custom renderers render `Q`.
  The bulk methods keep their collection arguments and inferred call syntax. Custom map types implement `Map` (entries
  and length) and `MapLookup<Q>` (lookup, usually one generic impl delegating to the wrapped map).
- **Breaking:** Capture mode is closure-scoped now. `AssertThat::capture(assertions)` runs the closure against the
  capture-mode assertion and returns the collected failures as `Vec<AssertionFailure>`, so a capture cannot be forgotten
  anymore. The closure receives the capture-mode `AssertThat` and must return it (or a mapped continuation of it). The
  fluent `verify()` / `verify_owned()` entry points work the same way and take the closure directly, e.g.
  `value.verify(|it| it.be_equal_to(42))`. Migration: `assert_that!(x).with_capture().is_equal_to(1).capture_failures()`
  becomes `assert_that!(x).capture(|it| it.is_equal_to(1))`, and builder calls such as `with_location(false)` move
  before `capture(..)` or into the closure. Failures were previously returned as pre-rendered `Vec<String>`. Where the
  old strings were compared, inspect the fields of `AssertionFailure` or render one with `.to_string()`. Panic-mode
  failure messages are unchanged.
- **Breaking:** The `Mode` trait is sealed and stateless now. `Panic` and `Capture` are plain unit type-state markers,
  `is_panic()` / `is_capture()` / `set_derived()` were removed, and failure behavior is driven by the new associated
  constant `Mode::CAPTURES`. Downstream `Mode` implementations were never able to integrate correctly and no longer
  compile. Since mid-chain mode conversions no longer exist, a derived assertion always shares its root's mode. This
  also removes a hazard where converting a derived assertion to capture mode silently swallowed its failures in the
  panic-mode root. `Panic` and `Capture` implement `Copy` now; because adding `Copy` can change how a non-`move` closure
  captures a mode value, use a `move` closure or explicit binding where capture by value matters.
- **Breaking:** Assertion-chain completion is no longer enforced by panicking destructors, in any feature configuration.
  Dropping an unused `AssertThat` no longer panics at runtime. Unused chains are caught at compile time by `#[must_use]`
  on the entry points, on every mapping or projection that could otherwise consume one without asserting, and on
  extracted owned subjects. A `capture` / `verify` closure that performs no assertions panics from the call itself, as a
  normal function panic. A double panic (process abort) can therefore no longer originate from this crate.
- **Breaking:** Variant checks no longer extract. `is_some()`, `is_none()`, `is_ok()`, `is_err()`, `is_ready()`, and
  `is_pending()` are plain chainable checks now. They keep the full subject and its mode, and work in both panic and
  capture mode. Extraction is a separate, explicitly named panic-mode operation: `get_some()`, `get_ok()`, `get_err()`,
  and `get_ready()` check the variant and then extract the contained value, borrowed for borrowed subjects and owned for
  owned ones. `is_none()` returns the full `Option` subject instead of an `AssertThat<()>`. The HTTP header-value
  extraction follows the same convention: `is_ascii()` is a non-extracting check now and `get_ascii()` extracts the
  value as a `String`. Migration:

  | before                                    | after                                          |
  |-------------------------------------------|------------------------------------------------|
  | `.is_some().is_equal_to(42)`              | `.get_some().is_equal_to(42)`                  |
  | `.is_ok().is_equal_to(42)`                | `.get_ok().is_equal_to(42)`                    |
  | `.is_err().is_equal_to(expected)`         | `.get_err().is_equal_to(expected)`             |
  | `.is_ready().is_equal_to(42)`             | `.get_ready().is_equal_to(42)`                 |
  | `.is_ascii().is_equal_to("v")`            | `.get_ascii().is_equal_to("v")`                |
  | `.is_ok()` as a bare variant check        | unchanged, and now also works in capture mode  |
  | `.is_none()` followed by chained `()` use | `.is_none()` continues on the `Option` subject |

- **Breaking:** `assert_that!(value)` borrows its input now. Named values remain usable after the assertion, and
  temporaries and literals live until the end of the enclosing statement, which is as long as the assertion chain needs
  them. `assert_that!(&value)` and `assert_that!(value)` are equivalent. Expressions yielding references to unsized
  targets (`&str`, `&[T]`, `&CStr`, `&Path`, `&OsStr`) keep the reference as their subject and borrow for the lifetime
  of the referenced data, so an assertion stored from `text.as_str()` remains usable on later statements. Assertions
  that consume their subject require the new `assert_that_owned!(value)` (or the fluent `.must_owned()` /
  `.verify_owned()`): the closure assertions `panics()` / `does_not_panic()` and their async variants, the terminal
  iterator assertions, and `unwrap_inner()`. Handed a borrowed subject, these panic with a message pointing to
  `assert_that_owned!`, reported at the consuming assertion's call site.
  `IntoAssertContext` now contains only the borrowing `must()` / `verify()` entry points and is implemented for `&T`
  and `&mut T`. Method-call autoref still makes them available on owned bindings. Sized shared and mutable reference
  receivers now both produce `AssertThat<T>`, matching `assert_that!`, so `reference.must()` works directly for
  `reference: &mut T`, exposes every pointee assertion (including downstream custom assertions), reborrows the
  reference, and leaves it usable after the chain. Mutable slices and strings use the necessarily sized shared-reference
  subjects `AssertThat<&[T]>` and `AssertThat<&str>`.
  The consuming `must_owned()` / `verify_owned()` methods moved to the new `IntoOwnedAssertContext` trait, whose blanket
  implementation preserves the exact receiver type: `(&value).must_owned()` still produces `AssertThat<&T>`, and
  `(&mut value).must_owned()` still produces `AssertThat<&mut T>`. This split replaces the previous blanket
  `IntoAssertContext<'t, T> for T` without specialized reference implementations or mutable-reference forwarding on
  each assertion family. Ordinary calls through the prelude keep their spelling. Code importing only
  `IntoAssertContext` for an `_owned` call must also import `IntoOwnedAssertContext`. Explicit bounds and UFCS calls must
  migrate from the type parameter `IntoAssertContext<'t, T>` to the associated subject
  `IntoAssertContext<'t, Subject = T>`, or to `IntoOwnedAssertContext<'t>` for ownership-taking calls.
- **Breaking:** The borrowing projection variants carry the primary names now, following `must()` / `must_owned()`:
  borrowing is the more useful default, taking ownership is the rarer case and gets the explicit suffix. `satisfies` was
  renamed to `satisfies_owned`, and the short name `satisfies` now denotes the borrowing variant (previously
  `satisfies_borrowed`, shipped in 0.6.1). Likewise, `derive` was renamed to `derive_owned`, and the previously private
  borrowing derivation is public as the new `derive`. The fluent aliases follow the same split as `satisfy` /
  `satisfy_owned`. `satisfy_borrowed` was removed. `satisfies_ref` keeps its name as the variant for unsized projection
  targets (`str`, `[T]`, ...), and `derive_async` keeps its suffix-free name because an async mapper has to produce its
  projection by value, so there is no borrowing counterpart to distinguish it from. Every affected call site fails to
  compile, because the mapper contract changes between returning an owned value and returning a borrow. Migration:

  | before                                               | after                           |
  |------------------------------------------------------|---------------------------------|
  | `.satisfies(mapper, ...)` with an owned-value mapper | `.satisfies_owned(mapper, ...)` |
  | `.satisfies_borrowed(mapper, ...)`                   | `.satisfies(mapper, ...)`       |
  | `.satisfy(mapper, ...)` with an owned-value mapper   | `.satisfy_owned(mapper, ...)`   |
  | `.satisfy_borrowed(mapper, ...)`                     | `.satisfy(mapper, ...)`         |
  | `.derive(mapper)` with an owned-value mapper         | `.derive_owned(mapper)`         |
  | `.satisfies_ref(...)` / `.satisfy_ref(...)`          | unchanged                       |
  | `.derive_async(...)`                                 | unchanged                       |

- **Breaking:** The satisfying callbacks hand out borrowed, value-typed assertions now. `is_some_satisfying`,
  `is_ok_satisfying`, `is_err_satisfying`, `is_ready_satisfying`, and the rootcause `has_current_context_satisfying`
  pass their callback an `AssertThat<T>` borrowing the inner value instead of the reference-typed `AssertThat<&T>`,
  matching what `assert_that!(&value)` produces. Type-specific assertion traits therefore apply inside the callbacks,
  e.g. `contains(...)` on a `String` inner value. The rootcause extraction `has_current_context::<E>()` likewise returns
  a value-typed `AssertThat<E>` borrowing the context. `is_ascii_satisfying` on `http::HeaderValue` keeps handing out an
  `AssertThat<&str>`, since the unsized `str` has no value-typed assertion form. Migration: closure type annotations
  drop the `&` from the element type, and expected values lose their `&` prefix, e.g. `it.is_equal_to(&42)` becomes
  `it.is_equal_to(42)`. Explicit uses of `RootcauseDynamicReportRefExtractAssertions` change from `<'t, 'r>` to
  `<'t, R = DebugRenderer>`: drop the report-reference lifetime and optionally name the renderer.
- **Breaking:** The `Condition` trait was renamed to `AssertrCondition`, following the `AssertrEq` / `AssertrPartialEq`
  naming. The broad name collided with other glob-imported preludes exporting a `Condition` (e.g. `bevy::prelude`),
  which made the bare name ambiguous at use sites. The trait's shape and the `is` / `has` / `are` / `have` assertion
  methods are unchanged. Migration: rename `impl Condition<X> for ...` to `impl AssertrCondition<X> for ...`, and
  explicit imports from `assertr::condition::Condition` to `assertr::condition::AssertrCondition`. The prelude exports
  the trait under its new name.
- **Breaking:** Fluent aliases of negated assertions always put `not` first now, matching the English imperative ("must
  not be equal to"). The alias generator derives `is_not_*` -> `not_be_*`, `has_not_*` -> `not_have_*`, and `does_not_*`
  -> `not_*` (the possessive `has_no_*` keeps its word order as `have_no_*`), so the spelling no longer depends on
  per-method overrides. Migration: `be_not_equal_to` -> `not_be_equal_to`, `be_not_poisoned` -> `not_be_poisoned`,
  `have_not_changed` -> `not_have_changed`. All other negated aliases (`not_be_empty`, `not_be_locked`, `not_contain`,
  `not_exist`, `not_panic`, ...) keep their names.
- **Breaking:** `MemAssertions::need_drop` is a generated fluent alias now and therefore requires the `fluent` feature.
  It was previously a hand-written, always-available synonym of `needs_drop`. Migration: enable the `fluent` feature or
  call `needs_drop()`.
- **Breaking:** `StringAssertions` and `StrSliceAssertions` were replaced by one generic `StrAssertions`,
  blanket-implemented for every `AsRef<str>` subject. `&str`, `String`, `&String`, `Box<str>`, and `Cow<str>` share one
  implementation, one set of bounds, and one set of failure messages. This closes the gap where `String` lacked
  `is_blank()` and `is_blank_ascii()`. `Box<str>` and `Cow<str>` implement `HasLength` now, too. Failure messages render
  the subject through the renderer, so a custom renderer used with `StrAssertions` must implement `ValueRenderer<S>`
  for the subject type `S` (`with_debug_format` provides exactly that). Expected and unexpected string arguments keep
  their ordinary `Debug` formatting. Migration: replace explicit imports of
  `assertr::assertions::alloc::string::StringAssertions` or `assertr::assertions::core::str_slice::StrSliceAssertions`
  with `assertr::assertions::core::string::StrAssertions`. Prelude users are unaffected.
- `Vec`, `[T; N]`, `String`, and `PathBuf` assertions no longer delegate to a derived slice, `&str`, or `&Path`
  assertion. The direct implementations keep the subject name set via `with_subject_name`, which delegation dropped, and
  no longer require renderers to implement `Clone`. `R: Clone` remains on everything that hands the renderer to a
  child assertion: the `derive` / `satisfies` families, `is_some_satisfying`, `is_ok_satisfying`, `is_err_satisfying`,
  `is_ready_satisfying`, `has_value_satisfying`, `has_type_ref`, and the `_satisfying` collection, map, and iterator
  assertions.
- Every negative assertion names its negation in its failure text now. `does_not_contain_matching` and
  `does_not_contain_satisfying` (collections and streaming iterators) report "unexpectedly contains ..." instead of
  "contains ...", and `has_no_remaining_elements` reports "Expected the iterator to have no remaining elements, but N
  remain." instead of the `has_remaining_count(0)` count comparison.
- Condition failures use the structured failure model now. The condition's error becomes an `AssertionFailure::details`
  entry instead of being embedded in the description, and every failing element of the per-element `are()` / `have()`
  assertions raises its own failure naming the element's zero-based index. Previously, per-element failures did not
  identify the failing element.
- The default build pulls 2 crates instead of 24, `indoc` and `num-traits`, and `--all-features` pulls 99 instead of
  141. No public item or feature was removed for this:
  - The `futures` facade is gone. It was pulled into every default build for a single `catch_unwind` inside
    `panics_async` / `does_not_panic_async` and is replaced by a dozen lines of local code that pin the future and wrap
    each poll in `std::panic::catch_unwind`. The assertions keep their `std` gate and behavior, but no longer require
    the future to implement `UnwindSafe`: every poll is individually wrapped in `AssertUnwindSafe`, matching the
    synchronous panic assertions and allowing ordinary futures such as `tokio::task::yield_now()`. The `std` feature
    carries no dependency of its own anymore.
  - The `num` umbrella crate is replaced by `num-traits`, which defines the `Num`, `Signed`, and `Float` traits the
    numeric assertions are bounded by. `num` re-exports those traits verbatim, so the `Num` bound of `NumAssertions` is
    the *same* trait and existing implementations keep working. Only code that names the bound itself has to depend on
    `num-traits` rather than on `num`. The `num` feature pulls in 1 crate instead of 7. `libm` is no longer a direct
    dependency, the `libm` feature only forwards to `num-traits/libm`.
  - The optional integrations request only what their assertions use: `tokio` gets `sync` instead of `full` (20 crates
    to 3), `reqwest` is taken without default features (99 to 69), and `serde` without `derive` (21 to 13). See the next
    entry for what this means for your build.
- **Breaking:** Updated the optional `reqwest` integration to `reqwest` 0.13 and the optional `rootcause` integration to
  `rootcause` 0.13. Users enabling either feature must update their direct dependency. `assertr` no longer enables
  `reqwest`'s default features (in 0.13 these include a `rustls` TLS stack backed by AWS-LC), `tokio/full`, or
  `serde/derive`. **If your build relied on `assertr` enabling any of those through Cargo feature unification, request
  them in your own dependency on the crate in question.**
- **Breaking:** The `std` and `libm` features no longer enable the `num` feature implicitly. Their edges into the
  optional `num-traits` dependency are weak (`num-traits?/std`, `num-traits?/libm`), so they only forward those features
  when `num` is enabled as well. The default feature set (`std` + `num`) is unchanged, so only users who disable default
  features are affected. Migration: with `default-features = false`, add `num` to the feature list to keep the numeric
  assertions, e.g. `assertr = { version = "0.7", default-features = false, features = ["std", "num"] }`. `std` without
  `num` is a supported configuration now and part of the CI matrix.
- The macro plumbing moved into the `__private` namespace. `assert_that!` and `assert_that_owned!` expand
  to `$crate::__private::assert_that_macro::{Wrap, Fallback, owned}` and `pattern!` to `$crate::__private::new_pattern`.
  The module `assertr::assert_that_macro` is gone and `Pattern::new` is no longer public. All three macros already
  routed through `$crate`, so call sites are unaffected. The affected items were `#[doc(hidden)]` macro implementation
  details rather than supported API. Build patterns with `pattern!`, the only supported way to keep a pattern's rendered
  source text and its predicate in sync.
- Assertion discovery now lives in a family-oriented rustdoc index and the authoritative assertion-trait pages. The
  manually maintained method catalog was removed from the README, which now points readers to IDE autocomplete and
  the rustdoc index. docs.rs builds every feature so optional integrations are included there.
- The README is a landing page now. The guides on capture mode, rendering non-`Debug` values, partial equality, custom
  assertions, and type assertions moved onto the API items that own them (`AssertThat::capture`,
  `AssertThat::with_debug_format` / `with_renderer`, the `AssertrEq` derive, `AssertThat::track_assertion`,
  `assert_that_type`), and the README links to them. The README is also the crate front page on docs.rs, and every
  Rust example in it runs as a doctest.
- **Breaking:** `AssertionRenderer<T>` was renamed to `ValueRenderer<T>` to make its responsibility explicit: an
  implementation formats one value of `T` for a diagnostic, not a complete assertion or failure. Rename downstream
  imports, implementations, and bounds. The concrete `DebugRenderer` and `CustomRenderer` types and the
  `AssertThat::with_renderer` entry point keep their names.
- **Breaking:** Assertion traits are implemented independently of renderer support now. The exact
  `ValueRenderer<U>` requirements live on the individual methods whose failure paths render `U`, so an unavailable
  capability no longer hides an entire trait. This fixes `PollAssertions`, `LengthAssertions`, and `NumAssertions`. It
  also makes the function, panic-value, range, path, HTTP header, Jiff, program, rootcause, command, and Tokio watch
  traits available on custom-renderer chains and preserves that renderer through their projections. Boolean,
  character, range, path, HTTP ASCII, Jiff, and program failure paths now honor the active renderer instead of
  formatting their subjects directly. Existing explicit trait paths keep `DebugRenderer` defaults where generics were
  added. To expose the method-level bounds, `LengthAssertions` and `PathAssertions` gained required `Subject` and
  `Renderer` associated types, `ProgramAssertionsRequiringPanicMode` gained `Subject`, and `NumAssertions` gained
  `Renderer`; downstream implementations must define them. Generic code calling these methods must add the method's
  new renderer bound (through the trait's renderer parameter or associated `Renderer` type). A renderer built with
  `with_debug_format` serves its subject type only, so a chain that derives to another type and asserts on it there
  (e.g. `derive_owned(|s| s.0 == 7).is_true()`) now requires `ValueRenderer<bool>`. Use `with_renderer` with a
  renderer implementing `ValueRenderer` for every rendered type, or reset the renderer before deriving.
  Structural assertions now compose their own diagnostics from leaf renderers consistently: a custom renderer
  implements `ValueRenderer<T>` for collection and iterator elements, map keys and values, range bounds, and values
  inside `Option`, `Result`, `Poll`, `RefCell`, mutexes, and locks. It no longer implements renderers for `Vec<T>`,
  slices, `Vec<&T>`, complete maps/sets, ranges, or those wrappers. Valueless failure states such as `None` and `Pending`
  require no renderer capability at all.

- `ProgramAssertionsRequiringPanicMode::exists_and` no longer clones its `Program` subject after locating the
  executable only to discard that clone during the projection to its path.
- References to arrays implement `HasLength` now, matching references to the other built-in collection subjects.
- Custom assertion descriptions that do not end with a newline are separated from the closing failure-message banner
  now, so the documented `AssertThat::fail(format_args!(...))` recipe produces well-formed output.
- The README's `AssertrEq` example compiles now. Its `Person` subject was missing the `PartialEq` derive required by the
  full equality assertion shown next to the generated partial matcher.
- `is_in_range`, `is_not_in_range`, `Command::has_arg`, `reqwest::Response::has_status_code`, the `http::HeaderValue`
  assertions, the tokio `watch` assertions `has_changed` / `has_not_changed`, the async function assertions
  `panics_async` / `does_not_panic_async`, and `assert_that_panic_by_async` report the caller's source location in their
  failures now. The synchronous implementations lacked `#[track_caller]`. The async implementations now capture their
  caller in a synchronous `#[track_caller]` shim and carry it through the returned future.
- `jiff`, `program`, `serde`, and `tokio` could not be enabled on their own: `--no-default-features --features tokio`
  and friends failed to compile, because those integrations wrap std-only crates without declaring the `std` edge. Each
  of them (and `reqwest`, `serde-json`, `serde-toml`) enables `std` now, and CI builds every feature in isolation from
  now on.
- `is_in_time_zone` reports the subject's actual time zone when it is unnamed, instead of repeating the expected time
  zone under `Actual`.
- `PathAssertions::has_file_name`, `has_file_stem`, and `has_extension` fail when the path has no such component now,
  instead of treating an absent component as a match.
- `contains_exactly` reports missing and unexpected elements when the collections have equal lengths but different
  element multiplicities, instead of misclassifying the failure as an element-order mismatch. Its diagnostics also
  retain relevant field-level differences reported by `AssertrEq`, matching exact-entry map failures, without leaking
  positional field differences when the elements only differ in order.
- Exact collection and iterator comparisons find a complete one-to-one assignment for custom `AssertrPartialEq`
  relations now. Overlapping expectations such as an `AssertrEq` wildcard followed by a specific field matcher no
  longer produce false missing/unexpected-element failures when reassignment can satisfy every expectation.
  Interchangeable expectations, such as repeated elements under plain equality, are still assigned greedily with one
  comparison per element, so duplicate-heavy inputs cost what they did before, and the search keeps its path on the
  heap, so no input size can overflow the stack.
- `contains_exactly_entries` no longer passes when the expected entries repeat a key, as in
  `[("a", 1), ("a", 1)]` against `{"a": 1}`. Each duplicate used to match the same actual entry. The entry count check
  catches it now and reports
  `Number of entries (1) does not match number of expected entries (2)!`.
- Operation-specific failure evidence no longer leaks into later failures in the chain. `does_not_panic()` and
  `does_not_panic_async()` report an `&str` or `String` panic payload as a per-failure detail, while successful
  `panics()` / `does_not_panic()` calls and their async variants stop attaching a misleading function-panic detail after
  the function behavior was checked.
- Failure messages of the `Result` variant checks spell the expected variant as `Result::Ok` / `Result::Err` now
  (previously `Result:Ok` / `Result:Err`).
- Fluent aliases preserve unrelated attributes that share a `cfg_attr` with `fluent_alias` or `no_fluent_alias`, and
  aliases for methods with late-bound lifetimes no longer forward those lifetimes through an invalid explicit
  turbofish.
- `BoxAssertions::has_type` reports an erased borrowed `Box<dyn Any>` value as `dyn Any` now, matching the owned path
  and its explanatory detail instead of displaying the box wrapper's type.
- `just verify` treats rustdoc warnings as errors now, matching CI so broken intra-doc links fail locally too.
- `panics_async()` and `does_not_panic_async()` catch a panic raised while invoking the function,
  before it returns its future. Polling the future was already caught, but a synchronous invocation panic escaped the
  assertion boundary.

### Added

- Numeric assertions via the `num` feature: `is_zero`, `is_positive`, `is_negative`, `is_close_to`, `is_nan`, etc.
- `Condition` trait for reusable predicates with `satisfies()`.
- `AssertrPartialEq` trait for field-by-field difference reporting.
- Assertion tracking (panics if `AssertThat` is dropped with zero assertions).
