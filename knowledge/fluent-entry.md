# Fluent entry and expression capture

[Architecture overview](README.md)

The `fluent` feature adds entry methods, aliases, and optional expression capture, using the same chain state and failure
handling as macro entry.

## Borrowing and ownership

| Entry | Storage | Completion |
|---|---|---|
| `must()` | Borrow receiver. | `Panic` chain. |
| `must_owned()` | Own receiver. | `Panic` chain. |
| `verify(...)` | Borrow receiver. | `Capture` callback. |
| `verify_owned(...)` | Own receiver. | `Capture` callback. |

Borrowing and owning methods use separate traits. Rust automatically borrows the receiver for `value.must()`. Calling it
on a reference reborrows the referenced value. Subject types and capture completion follow the
[entry rules](assertion-lifecycle.md#entry-subject-ownership-and-mode).
See [entry rustdoc](../assertr/src/entry/fluent.rs) for method-resolution examples.

Aliases preserve behavior and bounds. [Naming rules](../assertr-macros/src/fluent_aliases/naming.rs) derive spellings
such as `is_equal_to` → `be_equal_to`, `contains` → `contain`, and `matches` → `match_expectation`. Explicit overrides
cover unsupported names.

## Scoped expression capture

Plain fluent entry records no expression text. `#[assertr::fluent_expressions]` attaches the receiver's source text to
visible `must`, `must_owned`, `verify`, and `verify_owned` calls.

| Case | Behavior |
|---|---|
| Scope | Apply to a function or inline module. Other items and out-of-line modules are rejected. |
| Expansion | Place the attribute above test-style procedural attributes. It cannot see calls generated by later macro expansion. Renamed runtime dependencies work. |
| Callback | Never rewritten. The result of the call passes through `finish`, which attaches text to pending root failures of an `AssertionFailures` whose entry location matches. Other result types pass through unchanged. |

Verification never changes callback arguments, so callbacks keep their types, call traits, inference, and coercions,
including macro-generated callbacks. Visible fluent calls nested in the receiver or callback expression are processed
independently. A user-defined `#[track_caller]` `verify` or `verify_owned` whose result contains the failures of an
inner Assertr verification attaches the outer receiver text to them, because the entry locations match.
Implementation: [macro](../assertr-macros/src/fluent_expressions/mod.rs) and
[runtime helpers](../assertr/src/__private/fluent_expressions.rs).
[Callback fixtures](../assertr-macros/tests/fluent_expressions/03-callback-types.rs) pin the unchanged callback types.

### Pending attachment

Capture roots record privately whether expression text can be attached later. Mapping and renderer changes preserve
that state. Derivation clears it, and `with_expression` overrides it. Until attachment, `AssertionFailures` records which
failures can receive the text:

- Public expression fields show `None`, never a placeholder.
- Cloning preserves pending state. Equality ignores it.
- Owned iteration and vector conversion discard it.

### Name collisions

The macro identifies calls by method name. For unrelated verification callbacks and results, its fallback does nothing.
An unrelated `must()` call may fail compilation when rewriting adds `with_expression`. Keep such calls outside
annotated scopes.
[Fixtures](../assertr-macros/tests/fluent_expressions/) cover syntax and collisions.
