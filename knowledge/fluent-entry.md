# Fluent entry and expression capture

[Architecture overview](README.md)

The `fluent` feature adds entry methods on values and aliases for assertion methods. All fluent chains follow the
same [lifecycle](assertion-lifecycle.md) as macro entry.

## Borrowing and ownership

| Method              | Subject ownership  | Completion                                            |
|---------------------|--------------------|-------------------------------------------------------|
| `must()`            | Borrows.           | Panics on the first failure.                          |
| `must_owned()`      | Owns the receiver. | Panics on the first failure.                          |
| `verify(...)`       | Borrows.           | Collects failures from the callback's returned chain. |
| `verify_owned(...)` | Owns the receiver. | Collects failures from the callback's returned chain. |

Borrowing and owning entry methods live on separate traits. Autoref lets an owned binding call `must`. Reference
receivers reborrow their pointee and normally produce `AssertThat<T>`. Mutable unsized strings and slices reborrow as
shared `&str` and `&[T]` subjects. Calling `must_owned` on `&T` owns that reference.

Aliases follow mechanical naming rules. For example, `is_equal_to` becomes `be_equal_to`, `contains` becomes `contain`,
and `is_not_equal_to` becomes `not_be_equal_to`. Explicit overrides handle names the rules cannot derive. Source
assertion traits define the behavior and bounds of both spellings.

## Scoped expression capture

Plain fluent calls leave the failure expression empty because an ordinary method cannot read its receiver's source
spelling. `#[assertr::fluent_expressions]` rewrites visible `must`, `must_owned`, `verify`, and `verify_owned` calls
inside a function or inline module. It attaches the receiver tokens as the expression and supports renamed runtime
dependencies. Place it above `#[test]`-style procedural attributes so it sees the original body.

The rewrite can see a macro invocation used as a receiver. It cannot see fluent calls generated by a later macro
expansion. Out-of-line modules and items other than functions or inline modules are rejected. Verify callbacks,
including non-literal expressions, are adapted to attach the expression while preserving the returned chain.

Unrelated methods with the same names can be affected. User-defined `verify` and `verify_owned` calls have an autoref
fallback. An inherent `UserType::must()` is still rewritten and fails when expression attachment is attempted. Keep such
calls outside the annotated scope.
